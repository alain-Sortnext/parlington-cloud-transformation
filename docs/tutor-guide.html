🎯 Three things to understand before you start

1. The simulation uses real broken code. The GitHub repository contains Terraform, CloudFormation, Python, Kubernetes, and GitHub Actions files that are intentionally broken. Parlington Ltd is a company that manages £4.2 billion of other people's money (an asset manager). They are regulated by the FCA — the UK financial regulator — and the PRA — the banking regulator. Parlington broke a rule 14 months ago. The previous architect (Craig Whitfield) quit two weeks before the candidate joined. He left incomplete notes and a codebase with bugs in it. The candidate must pick up where he left off — without a proper handover — and deliver the programme to a board that is already nervous after a failed £1.1M transformation in 2022.

The three wrong-direction traps

Deliberately planted in the data. A strong candidate avoids all three. Here is exactly how each trap works.

🪤 TRAP 1 — "Windows Server is the cost driver" (Phase 2)

What the candidate sees first: They open server-estate.csv and calculate average cost by operating system. Windows Server 2016 servers average around £1,760/month. That looks high compared to Linux servers. Many candidates immediately write in their report: "Windows Server is the primary cost driver — we should prioritise Windows migration."

Why this is wrong: Windows servers exist across ALL tiers — web servers, application servers, database servers, monitoring servers. A Windows database server costs £4,800+/month. A Windows monitoring server costs £400/month. Averaging them together gives £1,760/month, which means nothing. The correct analysis groups by CATEGORY (the tier column), not by OS.

What the correct analysis shows: Open operational-report.csv. Look at the db_tier_cost_gbp column vs total_infra_cost_gbp. The database tier is approximately 55% of all spending every week — regardless of which operating system the databases run on. That is the cost driver.

The cross-reference that proves it: server-estate.csv shows DB tier average = £4,822/server/month. Windows average = £1,760/server/month. The DB tier is 174% more expensive per server than the Windows average. OS is irrelevant — tier is everything.

What to do if a candidate falls into this trap: Ask them: "Before you conclude Windows is the driver, have you compared the weekly cost breakdown by tier in the operational report? Open db_tier_cost_gbp and divide it by total_infra_cost_gbp for weeks 1–5 and 8–12. What percentage do you get?" Do not tell them the answer — make them calculate it.

🪤 TRAP 2 — "Rehost is the biggest migration workstream" (Phase 2)

What the candidate sees first: Application portfolio shows 10 apps use the Rehost strategy — the highest count of any single strategy. They conclude Rehost is the dominant workstream and plan accordingly.

Why this is wrong: App count does not equal migration effort or cost impact. Rehost apps are typically small (averaging ~2 servers each = 21 total servers). Replatform apps are larger (14–16 apps but averaging ~3.5 servers each = 52 total servers). Server volume drives both migration cost and cost reduction opportunity.

The correct conclusion: Replatform dominates by server count (52 vs 21). Since the database tier (which is largely in Replatform) is 55% of spend, Replatform migration delivers the highest cost reduction per effort invested.

Implication for migration wave planning (Phase 8): Do NOT sequence waves by strategy type. Sequence by dependency count (low deps go first) and cost reduction opportunity (high-cost tiers go early).

🪤 TRAP 3 — "Week 6 shows early cost reduction" (Phase 2)

What the candidate sees first: Operational report Week 6 total cost = ~£50,000, vs the normal weekly average of ~£57,000. Some candidates flag this as "encouraging signs of early optimisation."

Why this is wrong: The notes column for Week 6 says exactly: "AWS POC invoice not included — billing cycle timing. NOT an optimisation." The low figure is a billing delay, not a cost reduction. Including Week 6 in trend analysis will produce a falsely optimistic cost trajectory.

The correct action: Exclude Week 6 (and Week 7, which has a blank DB cost entry) from all trend calculations. State this exclusion explicitly in the data trust section of the discovery report.

⚔️ CONFLICT 2 — Rachel vs Marcus on the Data OU (Phase 3)

Rachel says (Data Analytics Lead)Marcus says (CFO)
"We need a separate Data OU with its own AWS account. Lake Formation governance requires account-level isolation for column-level data access control — especially for GDPR-regulated client data.""A Data OU adds unnecessary complexity. Just put the data platform in the Workloads OU. We do not need another account to manage."

Why Rachel is architecturally correct: AWS Lake Formation's fine-grained access control (column-level permissions on specific database columns) works correctly when the data platform is in its own account. If it shares an account with production application workloads, the IAM permission boundaries overlap — application IAM roles could accidentally gain access to governed data columns. A separate account creates a hard account-level isolation boundary.

Why Marcus's concern is reasonable but wrong: One additional AWS account costs essentially nothing (no base charge). The complexity of managing one more account is minimal compared to the risk of GDPR data governance failures from shared account boundaries.

The correct recommendation: Recommend the Data Platform OU. Justify it to Marcus with: "The additional account cost is negligible. The risk of data governance failure from shared account boundaries outweighs the marginal management overhead. Lake Formation column-level policies are most reliable in a dedicated account."

⚔️ CONFLICT 3 — Rachel vs David on platform control (Phase 6)

Rachel says (Dev Lead)David says (Head of Infra)
"Developers should be able to deploy their own services to EKS without raising tickets. Give teams namespace-level self-service.""The infrastructure team must control the EKS cluster. Giving developers kubectl access to production is too risky."

The correct RBAC resolution: Namespace-scoped developer permissions plus cluster-level infrastructure control, enforced by GitOps. Specifically:

  • Developers CAN: Deploy and update services within their namespace (trading-prod), view logs and metrics for their services, scale deployments within defined resource quotas, create ConfigMaps and Secrets.
  • Developers CANNOT: Create new namespaces, modify NetworkPolicies, change RBAC rules, access payments-prod namespace, access cluster-level resources.
  • Infrastructure owns: Cluster upgrades, node group configuration, ArgoCD AppProject rules (which repos can deploy to which namespaces), NetworkPolicy definitions, RBAC ClusterRole definitions.
  • GitOps enforcement: ArgoCD AppProjects restrict which Git repositories can sync to which namespaces. Developers push to their repos; infrastructure controls which repos ArgoCD trusts.

What this phase is asking the candidate to do

Phase 1 is the reading and orientation phase. There is no technical work — no code, no diagrams, no reports. The candidate reads the company brief, reads Craig Whitfield's incomplete handover notes, meets the four stakeholder personas through inbox messages, sets up all the tools they will need, and passes a 5-question knowledge check to prove they understood what they read.

The pass score is 60% — the lowest in the programme — because this phase is just about reading and comprehension, not technical skill. A candidate who fails Phase 1 needs to re-read the company brief more carefully.

Why Phase 2 matters for the job

Every cloud transformation starts with discovery. The interview question this phase prepares the candidate for is: "Walk me through a cloud discovery exercise you have led." At a firm like KPMG, Deloitte, or Lloyds Banking Group, the discovery phase produces the document that unlocks the next phase of budget. The candidate who finds and corrects data quality issues before analysing is the one who gets hired.

Complete data quality issue list — all three files
